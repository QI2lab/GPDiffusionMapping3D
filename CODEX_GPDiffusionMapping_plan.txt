STAGE 1: EXISTING 2D MODEL ON CPU AND GPU FLOAT64

1A. Establish simulations and a numerical baseline.

Use a small standalone validation script initially; the formal pytest suite belongs to Stage 3. Reuse an existing simulator if available and correct. Otherwise write one straightforward simulator for the paper's transition law:

    r_next = r + sqrt(2 * D(r) * delta_t) * standard_normal(2)

Use a constant field and one smooth positive spatial feature. Use explicitly chosen length/time units and fixed seeds. Generate the data once on CPU; feed identical arrays to CPU and GPU. Do not generate nominally identical datasets independently with different RNG libraries.

For the smooth field, use a finer simulator timestep as a second check against timestep bias. Use unbounded trajectories with a field defined everywhere, or a broad starting region and sufficiently short tracks. Do not add reflecting walls or clip trajectories without modeling that same physics.

1B. Port existing numerical operations.

- Initially keep the 2D input format and fixed deltaT unchanged.
- Use float64 arrays throughout the first GPU implementation.
- Move covariance construction, interpolation, prior arithmetic, and likelihood evaluation to CuPy.
- Preserve existing regularization and algebra; use CuPy equivalents of the existing factorizations/inverse operations.
- Keep data, covariance matrices, current diffusion values, and working arrays on GPU across proposals.
- Reuse buffers where straightforward. Avoid repeatedly copying full arrays to CPU.
- Preserve CPU proposal generation/control flow initially. Copying one decision scalar to CPU is acceptable for the first correct implementation; measure its cost before adding device-side control.
- Keep the existing CPU implementation working.

For d = 2, precompute a_j = ||delta_r_j||^2 / (4 * deltaT). Then:

    log_likelihood = -sum((d / 2) * log(D_j) + a_j / D_j) + C

C is independent of the proposed field. Either retain it everywhere or omit it everywhere; do not mix probability conventions between initialization and subsequent updates. Restore C when comparing the full Gaussian density.

For an existing transformed-coefficient proposal, reuse the existing incremental diffusion update. Evaluate its likelihood difference directly:

    delta_log_likelihood =
        sum(-(d / 2) * log(D_new_j / D_old_j)
            - a_j * (1 / D_new_j - 1 / D_old_j))

Reject invalid diffusion values using the existing mathematical positivity rule. Do not clamp them into valid values.

1C. Optimize only the measured bottleneck.

First validate a built-in CuPy likelihood. If proposal evaluation dominates, implement a fused ReductionKernel for the proposal's diffusion values, positivity condition, and likelihood contribution. Use RawKernel only if a measured bottleneck cannot be handled adequately by the simpler implementation.

Keep GP matrix operations in CuPy built-ins. Do not replace all numerical code with CUDA, build several permanent alternative engines, sparsify the kernel, or approximate the likelihood.

Check incremental field/prior updates against direct recomputation with the same regularized representation. Fix any confirmed inconsistency explicitly rather than relying on CPU/GPU agreement to hide it.

1D. Check numerical agreement and simulation inference.

Compare CPU float64 and GPU float64 on identical data and fixed field/proposal inputs:
- Covariance and interpolation results.
- Full likelihood, prior, posterior, and proposal log-acceptance ratio.
- Incremental updates versus direct recomputation.
- Positivity rejection.

For paired proposal checks, supply the same old state, proposal values, order, temperature, and acceptance uniform. Compare accept/reject decisions when the acceptance threshold is separated from the numerical error bound. Near-threshold rounding differences are not a reason to force matching decisions.

Do not demand identical entire MCMC chains: one borderline decision can cause valid chains to diverge. Compare independently run inference using recovered physical fields, Monte Carlo uncertainty, and multiple predeclared seeds.

Choose and record numeric tolerances before using them as gates. Relate them to float64 precision, accumulation length, and GP matrix conditioning. Report maximum errors and cancellation-sensitive log-ratio errors. Do not widen tolerances just to pass.

1E. Benchmark actual execution.

Warm up compiled kernels and synchronize the GPU for timing. Separately report initialization, proposal/sweep time, full inference time, and GPU memory. Include small and realistically sized simulation datasets with identical inference settings. Compare with warmed-up Numba CPU execution.

Report compilation/transfers separately from steady-state compute and include them in an end-to-end timing. A faster likelihood alone does not establish faster full inference.

Stage 1 gate: numerical and scientific agreement pass; the accelerated path genuinely uses GPU; measured benefit on a representative workload is documented. If full inference is not accelerated, identify the bottleneck and make only a small, evidence-based optimization before claiming this stage succeeded.

STAGE 4: SEPARATE, SIMULATION-DRIVEN 3D INFERENCE

Begin a separate commit series only after Stage 3 passes. Preserve the validated 2D path and its tests. Add 3D CPU tests to tests/cpu and actual-GPU/comparison tests to tests/gpu; keep the hardware suites separately runnable.

The 3D input is linked tracks with columns:

Use seconds for timestamps and the existing position-unit convention, with explicit scale conversion where already supported. No new linking algorithm.

4A. Write mathematical tests and simulations first.

Before implementing 3D inference, define the 3D Gaussian-density oracle and simulate:
- Constant diffusion at regular intervals.
- Constant diffusion with irregular intervals.
- A smooth positive 3D diffusion feature.

For irregular observations, simulate with finer internal steps where needed. Use identical simulated data for both backends.

Expected physics:
- Each component variance = 2 * D * delta_t_j.
- Mean-square displacement = 6 * D * delta_t_j.
- Sum_j ||delta_r_j||^2 / (2 * D * delta_t_j) follows chi-square with 3 * N_step degrees of freedom for independent constant-D increments.

4B. Make only the required code changes.

data_reader.py:
- Read ZYX and timestamps.
- Group by particle and sort within each particle by time.
- Construct consecutive within-particle position pairs and one positive delta_t per pair.
- Never form a displacement across particles or turn timestamp into a spatial coordinate.
- Reject duplicate/nonpositive intervals and nonfinite numerical input.
- Single-observation tracks contribute no transitions.

functions.py:
- Add the third coordinate to the existing isotropic kernel.
- Add a Z inducing coordinate to the existing rectangular grid. Start with a small grid.
- Use d = 3 and a_j = ||delta_r_j||^2 / (4 * delta_t_j).
- Broadcast or index each transition's delta_t correctly in initialization and likelihood code.
- Update the per-step and global initialization estimates:

    D_step_j = ||delta_r_j||^2 / (6 * delta_t_j)
    D_global = mean(D_step_j)

The last expression is the unequal-interval MLE under the constant, zero-drift, exact-position model. Do not replace it with sum(squared_steps) / (6 * sum(delta_t)).

model.py:
- Add nInduZ and optional nFineZ where needed.
- Keep the existing sampler and inference schedule.

plotting.py:
- Provide a simple XY slice at a chosen Z, with physical diffusion units.
- Avoid a new viewer or visualization framework.

Reuse the existing likelihood with a small dimension parameter where that reduces duplication. Do not generalize the entire application to arbitrary dimensions.
